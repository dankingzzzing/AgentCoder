# 评审演示与答辩说明

本项目选择 PPT 的代码审查方向。三个模型角色分别编码、审查、修复，由控制器管理交接和恢复。评分材料应展示实际行为，不能用 Agent 数量或“全部正确”等宣传替代证据。

## 三分钟操作路径

1. 启动 `python -m agentcoder serve`，进入标明“规则 Agent”的离线教学模式，选择“文本统计与稳定排序”。说明三个角色使用独立职责与交付协议。
2. 点击“编排流程”，选择带交付验收的模板，校验并保存。这里增加的是确定性规则节点，三个模型角色不变；它展示新增节点和修改交接无需改控制器。
3. 开始协作，指认审查失败、修复分支和复审通过。打开“迭代证据”，先看版本 0，再看版本 1：源码差异、问题数量、实际测试由 failed 变为 passed，测试哈希保持一致。
4. 打开“Agent 消息”，指认 code_ready、review_result、repair_ready 的发送方、接收方及哈希。状态和产物持久化，刷新仍能打开记录。
5. 下载完整交付包，在另一个目录运行 `python -m unittest discover -s . -p test_solution.py -v`。报告的验收结论与实际输出核对。

一分钟录像见 [demo.mp4](assets/demo.mp4)。实际真实模型结果与离线演示分别标注，不能把录像中的固定规则识别称为模型推理。

## 四个评分维度对应的证据

| 维度 | 打开位置 / 命令 | 可核对的事实 |
| --- | --- | --- |
| 完整性 40% | `python -m agentcoder evaluate`；[验收样例](samples/evaluation.md) | 三种任务、直接通过、两轮修复、预算终止、恢复、未实测十种预期行为 |
| 协作 30% | 消息页、版本回放、state.json | 角色交接有序；每轮代码与审查关联；冻结测试一致 |
| 扩展 20% | 编排窗口；`workflows/code_review_audit.json`；扩展与图校验测试 | 新增节点真正执行；非法回路启动前拒绝；已运行记录保留自己的流程 |
| 文档 10% | README、DESIGN、Desgin、视频、真实报告 | 使用命令、架构、边界、实际验证与可复现材料齐全 |

## 可回答的问题

**为什么同一个模型还能算三个 Agent？** 每个角色具有不同系统提示、专用工具 schema、输入和职责。控制器提交结果，再以消息和共享状态交给下一角色；不是单个提示声称自己切换角色。模型账号数量与角色数量不是一回事。

**如何防止“修复”只是改测试？** 修复 schema 没有测试字段。编码后的原测试逐字冻结，检查点还核验测试哈希；测试失败、语法错误或确认问题会否决批准。测试通过只证明已有回归契约，不能证明所有潜在缺陷都被发现。

**断网后会不会重新编码？** 从原检查点的当前节点恢复，已完成的编码交付保留。节点结果尚未提交的操作可能重做，属于至少一次恢复；有真实恢复和故障注入验收。

**十个场景全部通过说明什么？** 说明这十种编排行为符合预期，其中两个场景预期就是不获得代码验收通过；它不是 LLM 能力基准。真实模型调用报告单独给出。

**扩展能力和边界在哪里？** 注册新的 `run(state, context)` 实现，再修改 JSON 图。当前约束为一个编码、一个审查、至多一个修复和附加观察节点；处理单个 Python 标准库模块。任意 DAG、多文件仓库和公网部署未实现。

**为什么仍需手动允许执行？** Python 测试以当前用户权限运行。超时、输出上限和环境过滤是资源限制，不能代替安全沙箱。
